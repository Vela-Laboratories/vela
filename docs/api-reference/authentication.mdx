Vela uses ECDSA (secp256k1) signatures for all authentication. There are no API keys or passwords. Your Ethereum wallet is your identity, and your signatures prove you control it.

## HTTP Account Sessions

Private reads for balances, orders, fills, deposits, withdrawals, portfolio data,
and CSV exports require an account-bound bearer session:

1. `POST /auth/challenge` with `{ "address": "0x..." }`.
2. Sign the exact `data.message` returned by the server. Do not reconstruct it.
3. `POST /auth/session` with the address, nonce, and signature.
4. Send `Authorization: Bearer <token>` on private reads.
5. Revoke the token with `POST /auth/session/revoke` when signing out.

Challenges are single-use and expire after five minutes. Sessions expire after 30
minutes. Tokens are opaque and should remain in memory, not local storage. A session
for one wallet receives `403` if it attempts to read another wallet's records.

## Signature Scheme

Vela uses the same elliptic curve as Ethereum: **secp256k1**. Signatures follow the EIP-191 personal sign standard, which prepends a standard prefix to prevent signed messages from being mistaken for Ethereum transactions:

```
prefixed_message = "\x19Ethereum Signed Message:\n" + len(message) + message
hash = keccak256(prefixed_message)
signature = sign(hash, private_key)
```

The resulting signature is a 65-byte (130 hex character) value: `r` (32 bytes) + `s` (32 bytes) + `v` (1 byte, recovery id: 27 or 28).

## Order Signing

The browser ticket signs the v2 payload as a compact JSON array. The array order and
Rust enum spellings are part of the signature. Prices and quantities are integers
scaled by `1_000_000`.

```javascript
const order = {
  market: 'ETH-USDC', side: 'Bid', order_type: 'GoodTillCanceled',
  price: 3200000000, quantity: 1000000, nonce: 1,
  client_order_id: 'example-1', stp: 'CancelTaker',
  min_quantity: null, display_quantity: null,
};
const message = JSON.stringify([
  'vela:order:v2', order.market, order.side, order.order_type,
  order.price, order.quantity, order.nonce, order.client_order_id,
  order.stp, order.min_quantity, order.display_quantity,
]);
const signature = await signer.signMessage(message);
```

<Warning>
`stp`, `min_quantity`, and `display_quantity` are signed controls. Send
`signature_version: 2` with them, and use `null` in the signing array for
omitted optional fields. A changed control invalidates the signature.
</Warning>

The signed order is submitted as:

```json
{
  "market": "ETH-USDC",
  "side": "Bid",
  "order_type": "GoodTillCanceled",
  "price": 3200000000,
  "quantity": 1000000,
  "nonce": 1,
  "client_order_id": "example-1",
  "stp": "CancelTaker",
  "signature_version": 2,
  "signature": "0x...",
  "address": "0xYourEthereumAddress"
}
```

The API recovers the signer address and verifies it is the account wallet or
an active, scoped agent delegated by that wallet.

## WebSocket Authentication

The preferred flow reuses the HTTP session, avoiding a second wallet prompt:

```json
{
  "type": "session_auth",
  "address": "0xYourAddress",
  "token": "the-opaque-http-session-token"
}
```

The legacy per-socket challenge-response flow remains supported for non-browser
clients that do not create an HTTP session:

    ```javascript
      type: "auth",
      address: "0xYourAddress",
      signature,
      nonce: challenge.nonce
    }));
    ```
  </Step>
</Steps>

## Nonce Replay Prevention

The engine keeps a 20-entry window of accepted order nonces per account. It
rejects a duplicate. Once the window is full, it also rejects a nonce at or
below the smallest nonce still in that window. This permits concurrent orders
to arrive slightly out of order while preventing replay.

This prevents replay attacks: a signed order cannot be re-submitted by a third party who intercepts it, because the nonce has already been consumed.

Use a unique, safe integer for every signed request. A millisecond timestamp
can be a starting point for one browser session, but add a local counter when
multiple orders are created in the same millisecond. Coordinate nonce issuance
across processes that trade for the same wallet.

```javascript
let lastNonce = 0;
function nextNonce() {
  lastNonce = Math.max(Date.now(), lastNonce + 1);
  return lastNonce;
}
```

## Implementation: ethers.js

<CodeGroup>
```javascript ethers.js v6
import { ethers } from 'ethers';

const provider = new ethers.BrowserProvider(window.ethereum);
const signer = await provider.getSigner();

async function signOrder(order) {
  const message = JSON.stringify(order);
  return await signer.signMessage(message);
}

async function submitOrder(order) {
  const signature = await signOrder(order);
  const address = await signer.getAddress();
  
  const response = await fetch('https://vela-engine.fly.dev/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ order, signature, address })
  });
  
  return response.json();
}
```

```python Python (eth_account)
from eth_account import Account
from eth_account.messages import encode_defunct
import json

def sign_order(private_key: str, order: dict) -> str:
    message = json.dumps(order, separators=(',', ':'))
    msg = encode_defunct(text=message)
    signed = Account.sign_message(msg, private_key=private_key)
    return signed.signature.hex()

def submit_order(private_key: str, order: dict):
    account = Account.from_key(private_key)
    signature = sign_order(private_key, order)
    
    payload = {
        "order": order,
        "signature": "0x" + signature,
        "address": account.address
    }
    # POST to /orders
    return payload
```

## Address Derivation

The engine derives the signer address from the signature using the standard Ethereum address derivation:

1. Recover the public key from `(hash, r, s, v)`
2. Take `keccak256` of the uncompressed public key (64 bytes, without the 0x04 prefix)
3. Take the last 20 bytes → Ethereum address

This is implemented using the `k256` Rust crate in the engine.

## Security Properties

| Property | Guarantee |
|---|---|
| **Authentication** | Only the holder of the private key can produce valid signatures |
| **Order integrity** | Any modification to an order invalidates the signature |
| **Replay prevention** | Nonce high-water mark prevents reuse of signed orders |
| **No key exposure** | The private key never leaves the signer's device |
| **Standard scheme** | EIP-191 personal_sign — auditable and battle-tested |
