Honest trust model documentation matters. This page clearly states what Vela does and does not guarantee in the current public beta, and what the path to full trustlessness looks like.

## Current Status: Testnet Research Demo

Vela is not a production exchange. It uses synthetic and unverified demo credits, and no current flow should be treated as real-money custody. The table below is the ground truth.

## What Can Be Inspected Right Now

These properties are useful for research and testing, but they do not make the current system trustless:

| Property | How it works |
|---|---|
| **Order authentication** | Every order is signed with your ECDSA private key. The engine verifies signatures before accepting orders. No one can place orders in your name without your private key. |
| **Matching correctness (locally reproducible)** | The matching engine is deterministic. A developer with the required local batch data can replay transitions. Public, durable data availability is not currently guaranteed. |
| **Order book transparency** | The public WebSocket feed shows all resting orders in real time. You can verify that your order is in the book at the price you specified. |
| **Fill reporting** | Fills are reported via private WebSocket channels with tamper-evident data (order ID, fill price, quantity, is_maker). |
| **Open source** | The full engine source code is available on GitHub. The code you're trusting is the code you can read. |

## What Requires Trust in Beta

These properties are absent or require trusting the operator in the current demo:

<Warning>
Do not use real funds. These limitations are launch blockers, not acceptable production trust assumptions.
</Warning>

| Property | Current State | Planned Trustless Version |
|---|---|---|
| **Deposit custody** | ETH and USDC can exercise a Sepolia contract demo, while demo credits are maintained separately. Other deposit calls create unverified credits. There is no authoritative reconciled production ledger. | Audited custody vault plus finalized chain indexing and double-entry ledger credit. |
| **Withdrawal execution** | Production signing is disabled. Testnet requests are not backed by an atomic durable ledger reservation and have no completion guarantee. | Durable reservation, policy-controlled signing, broadcast tracking, and exactly-once reversal. |
| **Fraud proof enforcement** | The default proof provider emits placeholder records. There is no on-chain verifier or penalty. | Fixed audited prover, public inputs and data availability, and enforceable verification if retained in the final design. |
| **Censorship resistance** | No deployed forced-inclusion mechanism is active. | A separately audited and enforceable forced path in a later trust-minimization stage. |
| **Batch availability** | Batch data is local to the operator. The operator controls access and retention. | Publicly reproducible finalized balance data with defined retention and availability guarantees. |

## Risk Summary for Beta Users

The demo can lose or reset credits, become unavailable, report incomplete telemetry, or require manual intervention. Source-level determinism and ECDSA checks do not provide custody, solvency, availability, or recovery guarantees.

<Info>
**Required approach:** Use testnet assets only. Do not use real funds. Future guarantees require the ledger-first consumer-exchange milestones and external review; they are not promised by a date or legacy milestone label.
</Info>

## Planned Trust-Minimization Work

The current engineering plan first establishes ordinary exchange accounting and custody guarantees, then may add progressive trust minimization:

<Steps>
  <Step title="Stage 1 — Ledger-first exchange">
    - Audited on-chain custody vault
    - Authoritative double-entry ledger and finalized deposit indexing
    - Atomically reserved, policy-controlled withdrawals
    - Continuous asset-by-asset reconciliation and automatic halts
  </Step>
  <Step title="Stage 2 — Progressive trust minimization">
    - Commit finalized post-trade balance roots
    - Make finalized data independently reproducible
    - Add proof-based withdrawal rights and forced inclusion
    - Add enforceable fraud proofs or validity proofs if supported by the final audited design
  </Step>
</Steps>

## Comparison to Other Systems

| System | Deposit custody | Matching trustless | Censorship resistant |
|---|---|---|---|
| Centralized exchange | Trust exchange | No | No |
| Vela current demo | No production custody model | Locally reproducible with operator data | No |
| Vela Stage 1 target | Audited omnibus vault and ledger | Operationally controlled and audited | No |
| Vela Stage 2 target | Audited vault plus proof-based rights | Depends on final proof design | Planned |
| On-chain CLOB (e.g. Serum) | Smart contract | On-chain enforced | Yes |

The Stage 2 properties are design goals. They must not be described as guarantees until implemented, independently reproducible, audited, and deployed.
